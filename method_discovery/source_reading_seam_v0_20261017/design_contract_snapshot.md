# Working candidate: source reading and local revision

Research design, 2026-10-17. No new inference calls, Task continuations, evaluator runs, repository-code execution, or developer interaction were performed. This document proposes a falsifiable candidate; it does not recommend deploying it or altering the ongoing PoS transfer.

Terminology: “confirmation” is an ambiguous term in the requested discussion. Here it is working shorthand for examining and revising a claim's support, not a paper name, a new truth label, or a claim of verified correctness. Runtime behavior can remain ordinary source-reading prose and ordinary memory revision.

## Decision in one paragraph

The smallest coherent candidate is **one narrative-isolated source reading, followed by ordinary PMA reconciliation, followed by advice from the actually committed memory**. Its unit of confirmation is a consequential claim and its particular use, never the entire task. A fresh reader reconstructs both the requested boundary and the scope of recorded observations without the inherited bank or separately recorded diagnosis prose. The normal updater can accept, reject, narrow, or leave this reading unresolved, using older evidence. When it corrects its own interpretation, it replaces the safely identifiable active copy instead of merely appending criticism. The ordinary advisory channel communicates a useful correction or withdraws earlier advice when appropriate. Task retains its plan, experiments, implementation choices, and completion decision. This adds one model call to two-phase PMA, not a permission gate. Every semantic judgment remains fallible.

The candidate merits investigation only if its input boundary and retirement behavior beat cheaper source placement, ordinary memory maintenance, and generic extra review. A goal-only reconstruction is a useful subexperiment, but cannot be presented as a solution to the compressor's evidence-scope error. **Do not select it as a new core over PoS now:** PoS already constructs a goal before actor history, preserves the original user input in the actor view, audits belief updates, and replaces active state. Complete the separately planned PoS checks without adding this candidate's features. The remaining hypothesis concerns evidence-to-claim scope, the assumptions behind a consequential action, and whether an overclaim is actually retired and later revised.

## 1. The problem this candidate must actually address

The audited cases locate two distinct mistakes:

- **Sampler 07:** the raw task and correct density-interface memory `WSzu3voZ` were available. C0 nevertheless recommended unconditionally reverting the density-to-log conversion; F0 falsely attributed a log-density requirement to the task. The double-log demonstration can be locally correct while the proposed public-interface repair is wrong. The missing operation is appropriate use of already available authority, not retrieval of a lost requirement.
- **Compressor 14:** a full decode already produced zero bytes and a reported difference. A later debug harness produced a first integer, 180. Protocol-correctness confidence predates C0. C0 reasserted it, treated the prefix result as new proof, and extended exclusion of protocol mismatch to the current failure. The missing operation is limiting an inference to what its evidence establishes, including when an attractive explanation already occupies memory.
- **Nginx 18:** installation and intermediate configuration were compatible partial progress. Nothing in these observations justified an obstacle to proceeding. Keeping useful facts and pending work is part of success.

The recorded six cycles establish saved memory, Phase-2 visibility, and returned advice or silence. They do not establish delivery, Task acceptance, behavioral harm, or task-level improvement. Correcting the interpretation of those records is important: C0 amplified inherited compressor certainty; it did not demonstrably originate it.

The existing **54-call input-view diagnostic is a stronger warning against a cleanup-only story**. It used six exposed checkpoints, three identical-prompt repetitions per F/EB/E view, all Phase 2 only. F retained full input; EB removed outer analysis/narration while retaining the bank and commands/results; E also removed the bank. There was no stable winner. At sampler 235, E gave one contract-preserving reminder and two silences; at compressor 105, all three E outputs still overextended the prefix evidence, including one fabrication that all 180 items had been processed. EB often stayed silent. Removing narration also removes useful intent: in the SQLite fixture, Task already intended to try minimal tools, so silence cannot simply be labeled either missed help or success. These results constrain this proposal; they do not establish that an extra reader will work.

## 2. What “confirmation” means

Here confirmation means: **“This particular claim is currently supported strongly enough, within this stated scope, to use for this particular advisory purpose.”** It is a revisable model judgment. It is not a proof, an independent world observation, a vote, or certification of task completion.

Keep three questions separate:

1. **Authority:** what did the user ask for, and what genuinely authorized changes exist?
2. **Support:** what do the available actions, sources, and results establish about a descriptive claim?
3. **Use:** does that supported claim justify this advice now?

A correct answer to one does not settle the others. A successful local test cannot amend the public API. An explicit API requirement does not prove that a particular line must remain unchanged. A repaired memory entry does not prove that Task received or used a correction.

For analysis, distinguish these possible judgments about a focal claim:

- **Supported within scope:** retain or use the bounded statement, subject to revision.
- **Conflicted:** identify the incompatible requirement or observation and revise the affected interpretation.
- **UNKNOWN:** available evidence does not decide the claim, applicability, or causal explanation. Narrow an overclaim if appropriate without choosing its opposite.

These are distinctions for reasoning and evaluation, not mandatory runtime enums, labels, or output grammar. “Supported” describes the supervisor's fallible judgment, not a certified truth state; unresolved uncertainty may be expressed naturally without emitting the token UNKNOWN. No new status field or ontology is required. “Not supported” and “false” must remain distinct. Agreement between two calls reading the same sources adds no new observational support. Uncertainty must not block compatible Task work or become an excuse to withhold all ordinary help.

## 3. Minimum state and source semantics

The following are conceptual distinctions, not a new database schema.

| Object | Role | What it cannot do |
|---|---|---|
| Exact request and authenticated update stream | Normative authority, with ordering/version identity | Be rewritten by Task narration, a test, or supervisor memory |
| User-designated reference material | Authority only to the extent the user incorporated it into the request | Acquire broader authority merely because a file is called “reference” |
| Executed action/result records and source snapshots | Evidence of particular actions/results, with available object/version/test identity | Certify an author's interpretation of the output or all untested behavior |
| Task explanations, current plan, and public claims | Useful hypotheses and context for relevance | Change the user contract or become observations by repetition |
| Active PMA memory | Useful retained facts, procedures, progress, and fallible interpretations | Become more authoritative than its sources through persistence |
| Fresh source reading | A fallible candidate interpretation | Override older supported evidence or serve as an oracle |
| Write and delivery receipts | Evidence that text was committed or transmitted | Establish the text's truth, Task understanding, or behavioral effect |

Existing task/event/bank identifiers suffice. Do not create a universal causal graph. Preserve raw source records and use the existing bank as the active state. The only additional bookkeeping needed for retirement is an ordinary run-trace record of the exact old span, its replacement or removal, the source/state version, and any corresponding delivered advisory. The archive is reversible history, not another equally current instruction automatically appended to every prompt.

Origin labels do not certify truth. A tool can print a mistaken Task-authored assertion; a quoted source can be interpreted incorrectly; an exact hash identifies bytes rather than meaning. A source whose identity or applicability is unresolved stays unresolved.

## 4. Trigger and input isolation

### When the extra reading runs

Initially run it at the **existing PMA wake points**, with no new high-frequency monitor and no oracle detector of a wrong diagnosis. This makes selection auditable. A future selective trigger would be a separate claim requiring evaluation.

Reconciliation focuses on a claim when its purported support would change a consequential choice: redefine a requested boundary, exclude a still-live explanation, justify skipping relevant evidence, recommend undoing compatible work, or preserve a misleading assumption for later wakes. Mere incompleteness, ordinary uncertainty, or an intermediate action is not a conflict. Finishing the task does not create a new approval obligation.

Select relevance from the actor's public pending move or the supervisor's proposed advice, not an invented plan. Ask which assumption makes that move appropriate. An unconditional public-interface change presupposes permission to change the boundary; excluding mismatch presupposes discriminating evidence. In contrast, trying a decoder-loop experiment does not require first proving the loop is the cause. Exploration can rationally proceed under UNKNOWN. The mechanism examines an action's asserted justification; it does not require every action to be justified by a confirmed causal theory.

### What the fresh reader receives

- The complete exact request and genuinely authenticated updates, including authoritative attachments or references already available to the host.
- The executed action/result records made available at that normal wake, including command/test content and available source/version identities.
- An explicit account of mechanically missing or truncated input, where applicable.

It does not receive the old bank, previous supervisor conclusions, case labels, evaluator scores, expected answers, researcher-selected decisive clauses, or separately recorded Task diagnosis prose. It does not first receive a focal bad claim, because that would inject the frame the boundary is intended to exclude.

The source window must be selected by an event rule fixed before results are seen, for example all complete action/result pairs in the host's ordinary observation window. If a budget requires truncation, use a fixed, pair-preserving rule and disclose the cut. Do not construct a hand-cleaned “right evidence” packet and call that online selection. If the host cannot distinguish typed records from prose reliably, report that limitation; do not invent provenance by regex or silently claim isolation.

Command comments, code, tests, and printed output can themselves contain diagnosis. Therefore this is **isolation from specified narrative channels**, not complete decontamination. Archive exact reader packets. The source-only view may contain Task-authored tests with narrow or mistaken assertions.

### What the reader produces

A short ordinary-language source reading: requested boundaries; what the actual records show; what important conclusions remain unresolved; and source pointers or exact spans. It does not propose a repair, declare completion, or decide whether Task must stop.

Illustrative generic instruction, to freeze before testing:

> Describe what the supplied request requires and what the supplied executed records establish. Distinguish those two roles. Preserve the scope and identity of each result. Mark unresolved implications as unknown, including missing context. Cite the relevant supplied spans. Do not infer new user instructions, diagnose a repair, or decide task completion.

This wording is not the mechanism's claimed novelty. The enforceable change is the input boundary.

Unlike the earlier E/EB projection, this first stage performs an actual separate source-reading computation, and its provisional result is subsequently reconciled with restored useful memory and intent. Simply dropping the bank from Phase 2 and renaming that “reference construction” would repeat the already tested projection. The extra computation still needs a matched exposed-reader control; a different call structure is no evidence of better judgment.

**An important tradeoff:** the minimal one-extra-call design presents the task and source records together. It is not the stronger goal-only isolation implemented in `reference_revision_v0`; technical records may still bias the reading of the request. Conversely, the goal-only helper cannot independently assess the compressor observations. Do not hide this tradeoff by calling both “blind reference.” If the combined reader fails either role, that is a failure of this minimal candidate. Adding separate readers is a new, more expensive variant requiring its own justification, not an automatic rescue.

## 5. Reconciliation: the actual confirmation operation

Reuse PMA Phase 1. It receives the fresh reading, the full raw request and ordinary observations, the previous bank, and the Task's current public activity. The fresh reading has no veto and no privileged truth status.

**Default wiring: the source reader's output R goes only to Phase 1.** Supply it as ordinary supplemental prose in that call. Keep PMA's existing memory tools, argument schemas, stored entry shapes, and CRUD semantics unchanged. Revision is expressed through the existing status/save/update/delete operations, not new tools, required fields, or a separate serialized confirmation protocol.

For a consequential claim, the updater asks a local question: **“What permits this assertion to be used in this way, under the user's actual request?”** It must distinguish:

- a normative statement from a descriptive statement;
- the observation itself from an explanation of it;
- a result about this object/version/test from a claim about other objects or general behavior;
- a useful possible next step from a claim that alternative explanations have been ruled out.

If it says an explanation is excluded, there must be some relevant observation or authoritative boundary that distinguishes it. Merely repeating a test result compatible with both explanations cannot supply that exclusion. A competitor need not be invented when the existing scope is already clear; no mandatory adversarial essay is required.

When the sources disagree, handle the conflict rather than tallying votes:

1. **Task prose versus an explicit user instruction:** the user instruction supplies authority. The implementation remains free to satisfy it in different ways.
2. **New user update versus old reference:** the authenticated ordered update changes the requirement. Rebuild stale derived readings; do not let old memory veto it.
3. **New result versus an old descriptive claim:** first compare object, version, test, and scope. An old pass and a new failure may concern different implementations. If identity is missing, keep that uncertainty instead of pretending direct contradiction.
4. **Fresh reader versus older source-backed knowledge:** inspect the older support. The fresh reader may have lacked it and may lose. Absence from its window is not disproof.
5. **Underdetermined diagnosis:** preserve the observed facts, retract unwarranted certainty, and leave the cause UNKNOWN. A bounded useful suggestion can survive withdrawal of its overstrong rationale.

No appeal to a hidden evaluator is permitted in runtime decisions. No requirement to prove the entire task or satisfy a supervisor-chosen plan is introduced.

## 6. Correction, retirement, and actual delivery

### Correction and retirement inside the supervisor

When reconciliation changes a supervisor interpretation, use existing status/update/delete operations to make the revised interpretation the active one. Identify exact permissible target entries or spans. Receipt-backed authorship makes a span editable; it does not make it incorrect.

- Preserve the user request, observations, completed-action facts, side effects, and useful unrelated procedures.
- Revise only the inference that exceeds them. For a mixed entry, retain the observation and valid constraint while narrowing the conclusion. If the clauses cannot be separated safely, do not delete the whole entry. Record incomplete repair and, if useful, make a bounded advisory correction.
- Inventory affected active copies, including inherited ones. In compressor 14, changing only the new C0 knowledge item does not remove older protocol certainty. Different paraphrases require fallible semantic identification; exact-string search cannot certify complete retirement.
- Read back actual committed memory before constructing Phase 2. A partial or failed write is not a successful correction. Use the actual state or ordinary fallback; never pause Task for this infrastructure failure.
- Archive the superseded supervisor text and receipt. Do not replay that text as current guidance on the next wake. Reinstatement remains possible when genuinely new evidence supports it.

The candidate only retires targeted supervisor-owned active interpretations. It does not erase Task's history, rewrite Task's plan, remove every occurrence from every source, or claim to eliminate all contextual influence. If preserved narrative repeatedly recreates the overclaim, measure that as recurrence rather than claiming successful durable repair.

### Advice and withdrawal to Task

Reuse PMA Phase 2's original prompt builder, system instruction, parser, and reminder/silence interface. It sees the exact request, current observations, and **actually committed** bank. **Do not separately re-inject R into Phase 2.** Any source interpretation that persists must arrive through ordinary committed memory. This isolates whether the new reading repairs active memory and prevents a direct helper hint from masking an incorrect bank. A correct bank followed by wrong advice remains a decision-use failure. Phase 2's decision remains about useful assistance now.

- A corrected bank can warrant silence when Task is already handling the issue.
- A correction relevant to a pending harmful move can warrant one short reminder with its basis and scope, without prescribing an entire replacement plan.
- If a wrong supervisor advisory was demonstrably delivered and may still be relied on, explicitly withdraw the affected part. Do not falsely say “I previously told you” when only an undelivered proposal exists.
- An actor response or later source receipt may show that the warning was mistaken. Reconcile it on the next ordinary wake, revise the supervisor's state, and withdraw the warning when warranted. Task does not need permission to disagree or continue.
- Do not repeat an unchanged warning when Task is already responding to it. New evidence or continuing material reliance can justify an update; lack of a ceremonial acknowledgment cannot.

The host logs the actual reminder insertion into the next Task request, not just `should_inject` or a returned advisory string. Keep four outcomes separate: memory committed; advisory delivered; subsequent Task behavior compatible/incompatible/unknown; eventual task outcome. None implies the next. Observed compatible behavior is not proof of the actor's private reasoning or of causal mediation.

## 7. Concrete behavior on the three anchors

### Sampler

A sound correction preserves the density-facing public contract and states that the double-log probe demonstrates a representation mismatch in the inspected call chain. It does not establish that the contract should change to log-density. Removing a redundant internal conversion remains allowed if a suitable public boundary performs the conversion exactly once elsewhere.

If the actor is about to follow an unconditional revert, suitable bounded advice would be: “The requested callback is a density function. The double-log result identifies a mismatch in this test, so preserve that public boundary while deciding where the single conversion belongs.” This is an illustrative output for evaluation, not a hint to put into the generic mechanism prompt.

### Compressor

Retain “full decode produced zero bytes / reported difference” and “the debug harness printed first integer 180.” Replace unsupported protocol proof and current-failure mismatch exclusion with their actual narrower scope. Do not infer 180 executed operations, a minimum size for 180 operations, truncation, or the unique cause of the failure from those records.

“The first-integer probe does not establish full-stream compatibility; the cause of the zero-byte result remains unresolved” is already a successful narrowing. It need not diagnose the true encoder bug. If Task is already investigating the decoding loop, useful memory repair can coexist with silence. Do not ask for the already failed full decode merely to fill a checklist.

### Nginx

Retain the successful configuration change and relevant names, retain pending work, and let Task proceed. No demand to validate the whole deployment before making the next compatible edit. Silence is acceptable here, but a method that stays silent everywhere has not demonstrated useful supervision.

## 8. Safeguards when the auxiliary reading is wrong

These reduce exposure; none guarantees semantic correctness.

1. The raw task and evidence remain available downstream. The helper never replaces their access.
2. UNKNOWN is accepted, including an unresolved reference to an unavailable existing API. The helper must not invent the missing API.
3. Old useful facts are not discarded because the fresh packet omitted them. Reconciliation can reject the fresh reading.
4. Changes are limited to identifiable supervisor-owned interpretations and are reversible. Source origin or quotation matching alone is insufficient justification for a semantic rewrite.
5. Failed, malformed, or absent helper output yields an explicit failed-method receipt and ordinary PMA fallback. There is no actor lock and no silent claim of successful confirmation. Report the helper failure separately from fallback behavior: whether ordinary PMA was attempted, what it actually committed/delivered, and whether a subsequent Task request or action was observed. If Task continuation was not run or cannot be observed, say so. “Fallback permitted” does not establish that Task continued, and a successful fallback is not a successful invocation of this candidate. This reporting uses the ordinary run trace, not a new mandatory memory grammar.
6. Corrective advice is itself revisable from later source evidence. The supervisor's earlier correction must not become a new permanent dogma.
7. Read-back and delivery receipts distinguish what happened mechanically from what is merely proposed. They do not turn a semantic opinion into truth.

At runtime the source reader and reconciler can share a model and shared blind spots. No majority vote, pseudo-Bayesian confidence increase, or uncalibrated sequential test is justified by their agreement. The design makes failure boundaries inspectable; it cannot make arbitrary LLM semantic judgments mathematically reliable.

## 9. ProCo: useful analogy, concrete non-transfer

The research record reports a read-only audit of official ProCo `code/prompt.py` at commit `4aec09fcafe375a5029c80e7e5bf28a16b18aad6` in `wzy6642/ProCo` (Apache-2.0). This report was supplied during this design review; I did not independently execute or re-audit that repository.

The useful idea is checking a solution against a particular recovered condition rather than asking a generic “are you sure?” But the reported implementation accepts verification output lacking “incorrect”; its pipeline can terminate even after a negative judgment when recovered/original condition edit distance is at most five or one string contains the other. **“density” and “log-density” differ by four insertions and have a substring relation**, despite denoting materially different callback contracts here. Those acceptance predicates cannot be transferred.

Nor should they be replaced by exact-string equality as the truth criterion. Equivalent conditions can be worded differently; a verbatim recovered condition can coexist with a solution that violates it; inverse condition recovery may be nonunique. An uncertain or unparsed judgment is UNKNOWN, not confirmation. Lexical checks can identify spans and validate packet structure, never certify semantic compatibility. This candidate does not need a masked-condition reconstruction module unless a separate experiment shows incremental value beyond its cost.

## 12. Cheap baselines and experiment order

Do not immediately stack all modules and compare only with historical C0. The existing outputs are failure anchors with disclosed provenance/order qualifications, not new matched controls.

1. **Zero-extra-call source placement.** Use ordinary PMA and move the exact full request/updates into a salient source section without hand-selecting the density clause. Preserve all evidence. The current prototype's `raw_replay` duplicates the raw task; it is a related cheap control, not an implementation of lossless movement.
2. **Narrative-exposed extra reader.** Same source-reading instruction, downstream calls, and budget cap, but let the reader see bank/narrative. This tests the input boundary beyond merely spending another call. Report actual tokens/latency and differing input lengths.
3. **Generic extra review.** A matched ordinary draft/review opportunity can test whether source decomposition adds value beyond extra reconsideration. Add this only if a claimed architectural advantage survives the cheaper tests.
4. **Existing PMA correction and direct bounded advice.** If ordinary maintenance already makes and persists the correct narrowing, no separate projection system is necessary. If one immediate correction suffices for the current decision, count that benefit without claiming bank repair.
5. **Deletion-only.** For a replacement claim, generate one shared revision and compare four copied banks: old retained; old plus revision; old removed only; old replaced by that same revision. Preserve source facts. Replacement versus append tests continued old-text presence; replacement versus deletion tests the value of the new text. Neither identifies a private psychological cause.

Use a staged falsification program, not an unbounded series of prompt patches:

- First determine whether the source reading correctly distinguishes both normative authority and observation scope, and whether reconciliation can reject an intentionally wrong reading. The existing goal-only adapter cannot establish the observation-scope part.
- Test retirement only after a correct revision can actually be produced, with the shared-text controls above. Inventory surviving inherited copies and disclose residual narrative influence.
- Only then test the normal multi-wake path and actual delivery, with separately authorized Task continuation. Keep autonomous completion and the original tools unchanged.

The `reference_revision_v0` artifact reports 203 mechanical checks, scripted placeholders, frozen Phase-2 screens, and separate two-phase smoke tests. Its runner accepts only scripted transports and has no real provider path. Those checks demonstrate packet/adapter properties, not semantic quality, retirement, Task delivery, or outcome improvement. This design does not convert those checks into evidence for the larger candidate.

## 13. Measurements and stopping rules

Record separately: request fidelity; evidence-scope fidelity; wrong-helper rejection; retention of useful facts/procedures; correctness and completeness of active retirement; recurrence on later wakes; helpful interventions; unnecessary interventions; appropriate silence; actual delivery; Task response; task outcome; calls/tokens/latency. Keep UNKNOWN frequency and usefulness visible, so universal abstention cannot win by avoiding false assertions.

Freeze prompts, packet construction, input versions, model/profile, order, resource cap, and evaluation rubric before future calls. Review against raw public tasks and receipts, blind to arm where possible. Keep disagreements and full traces. Do not put expected answers or hidden evaluator results into runtime inputs. A small diagnostic screen supplies case-level evidence, not an efficacy percentage.

Stop or narrow the claim when:

- the fresh reading is wrong: construction remains unresolved;
- the reading is correct but harmful advice persists: reconciliation/use remains unresolved, so stop elaborating the extractor;
- 07 improves but 14 fails: report an authority-reading result, not a general confirmation solution;
- correction is good but the old assertion returns: persistence remains unresolved;
- memory is repaired but delivery/use is absent: stop at that earlier endpoint;
- legitimate work is obstructed or useful old facts are erased: the general-supervision claim fails;
- simpler placement, ordinary CRUD, or deletion matches the candidate: keep the simpler method;
- only a manually supplied correct interpretation works: report an oracle-assisted conditional capability, not autonomous repair.

One decisive retained failure prevents claiming that the method solves these anchor fixtures. Passing them earns held-out testing, not a guarantee and not immediate deployment. Do not rescue each counterexample by adding another mandatory field, reader, or release gate.

## 14. Bottom line and provenance

The research question is narrow: **does isolating the supervisor's first source reading, then selectively reconciling and retiring its own interpretation, improve advice and durable memory under an unchanged user contract without reducing Task agency?** The contract makes authority, evidential support, and delivery distinguishable. It does not supply a semantic oracle.

The ProCo implementation details are explicitly reported from that separate read-only audit. No new primary-paper claims are introduced here.

The lineage review already establishes relevant antecedents: RER changes context but can preserve an exclusion frame; root_records removes narrative channels but can lose useful material and retain contamination elsewhere; PoS repairs a derived belief state without guaranteeing entailment; contextual filtering isolates an initial strategy; SSC changes the conditioning used after revision. These prevent presenting another fresh call or a new name as novelty. Any defensible contribution would be the measured, autonomy-preserving confirmation/revision behavior and its failure boundaries, not a claim to have invented self-critique or semantic guarantees.
