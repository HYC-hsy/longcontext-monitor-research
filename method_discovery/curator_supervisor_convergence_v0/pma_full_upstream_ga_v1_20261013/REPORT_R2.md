## Concrete fixes and limits

`PMAEpisode._actor_step` maps the entire public GA `response.content` into upstream `analysis` only when GA has no structured analysis; `plan` remains absent. The original event is retained verbatim. Hidden `response.thinking` is never read. An independent original `_run_agent_loop` fixture and actual GA event adapter produced equal phase-1/phase-2 prompts, system texts and serialized tool schema for a distinctive public response, two tools, two results, and a parse-error actor-attempt hole. Separate original-loop comparisons cover initial phase-1 and phase-2 injected failures; lower transport audit records each phase status while leaving upstream's catch-and-continue behavior intact. This does not prove every original Terminus2 feature maps to GA (e.g. its actor-only summarization remains unused).

GA now calls `task_end` before publishing `done`/`[ROUND END]`. It forwards the original terminal `result` to the JSON event instead of serializing potentially non-JSON tool data; the full original Task outcome remains in GA's local completion path. The Task terminal receipt now has a separate `pma_finalization` field. A successful PMA end is not inferred from `CURRENT_TASK_DONE`: the host worker must actually save both `memory.json` and `trajectory_memory.json`, write the event receipt, then exit. A second-artifact save failure records `save_failed` and never marks a clean PMA end. Worker exit and saved state are distinct from Task completion and from Harbor return code.

The worker has its own absolute deadline, stop file, in-flight cancellation attempt and host-only fallback save. A deadline in-flight test produced no late Task receipt, marked remote execution unknown and saved local state without claiming a normal `task_end`. If an underlying provider ignores cancellation, the launcher has a ten-second grace then kills that worker; absence of a worker exit receipt is a failure, not clean shutdown. No later PMA result is sent after the deadline. The fallback save performs no model call. Original LiteLLM retry and upstream phase failure handling are unchanged; a remote call's service-side completion or cost can remain unknown.

`offline_launcher.py` is unarmed and rejects `--execution-authorized`. It selects the SHA-pinned research Harbor adapter, creates a fresh public task package and isolated source bundle, starts one host worker only for B, mounts only request RW/response RO into the Task container, routes GA inference to the existing local Unix-socket fake gateway, then verifies worker exit and absence of owned Docker containers. It does not create a Monitor, invoke a native verifier, or install the vendor PMA into GA. The worker's private bank, source tree, raw prompts and credential configuration are outside all recorded Task mounts. Actual Docker inspect shows the main container on each target image, network `none`, request RW, response RO, no host-private mount. The official image `/tests` and `/solution` are absent before Harbor setup; the public Harbor package has empty test/solution directories. Task-side write access to its own request spool is a protocol trust limit, not an OS proof against malicious event forgery.

## Remaining live-start questions

This stage does not authorize or certify a live four-arm run. The unarmed launcher cannot be used to bypass approval. A separately audited live launch must bind four fresh run IDs, manifest and code hashes, real PMA 4.6 endpoint/profile behavior, a shared wall-clock budget, and a verified native-evaluation barrier to each final frozen artifact. Official verifier outputs are not present and cannot be inferred from Harbor `return_code=0`. A task-side process sharing the GA container can see the spool request mount; this design assumes Task code does not adversarially forge PMA protocol events. If adversarial authenticity is required, that trust boundary needs an independent design decision before live use. Old Fyne/Kitex scores and this scripted fixture are not controls for the future Terminal-Bench comparison.
