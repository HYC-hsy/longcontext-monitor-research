Runtime chain and method differences
------------------------------------
The original Task and public GA history remain stateful. PoS reset commits
before the configured first PMA trigger. One completed actor decision/tool
batch becomes one PoS joint-action transition. At a wake, PMA Phase 1 sees
the original task plus the configured recent actor-step window, not PoS
interpretation; Phase 2 alone sees the revisable current state and the last
delivered suggestion with actual subsequent results. The candidate's PMA
status tool is absent from its schema, fallback dispatch and bank rendering;
original U is unchanged. Knowledge/procedural CRUD, search, parser and trigger
remain pinned upstream. PoS update/audit/revision remain pinned upstream;
candidate changes are explicit in candidate.py/memory_adapter.py.

Each new bank entry has a sidecar content hash, bank version and input-visible
event IDs. The actual Phase-2 bank formatter records selected IDs; no extra
BM25 search is run. These IDs mean input availability, not sentence support.
Old entries with no sidecar have unknown provenance. A suggestion freezes at
most four selected old events, each with bounded visible tool-return segments,
and binds that package to the suggestion text/hash only when the advice enters
an accepted Task request. On the next real transition the same frozen package
is visible to updater and audit; consuming its cursor does not erase the
record used by the next PMA Phase 2. No advice is re-sent automatically.
accepted_revision changes only on an accepted structural state change;
upstream belief.step retains its own scheduling semantics. A rejected update
leaves the prior accepted revision marked as retained; a no-change commit is
separate. Task remains free to act or finish, regardless of gaps/advice.

Independent citation repair is `visible_tool_fields_v2` (5d00c352 and later
configuration binding). Only a field/segment actually shown in the audit
request can justify a literal quote. Host next_prompt, tool arguments, model
advice and metadata do not acquire tool-return provenance. Decoded text is not
unescaped again: literal backslash-n is not a real newline. Head/tail segments
cannot be stitched across omitted middle content. Original PoS mode remains
selectable. This is source-literal checking, not semantic entailment.

Transport and budget
--------------------
Profile candidate PMA calls are not routed through the Task sink. A separate
host-side worker loads the existing private PMA profile by exact SHA-256 and
reuses construct_upstream's pinned LiteLLM adapter, including its 3-attempt
decorator and profile parameters. The candidate bank remains in the isolated
PoS worker; Phase 1/2 each uses one bound event-spool command ID and no spool
replay. The host worker participates in the existing ready/stop/exit barrier.
Actual profile resolution in the no-network test: claude-opus-4-8,
adaptive thinking, temperature 1, max_tokens 8192, read_timeout 300 seconds.
PoS role profile path retains its existing belief 4096 and consistency/
progress 512 output caps, disabled thinking, temperature 0 and zero transport
retries. Task profile and complete-response policy are not changed here.
The future profile path is implemented, not authorized or provider-tested.

The resolved candidate trigger is interval=1, first_step=true, recent actor
window=8, step=actor_attempt+1. Frozen config and worker binding must match.
Task panel and Phase-2 advisory caps are 16,000 Unicode characters each;
revision_context 12,000; up to four historical events x 2,000 characters and
eight direct related state records. Optional overlong advice is dropped whole.
The additional candidate-only complete-request guard is 90,000 UTF-8 bytes:
the final serialized Task/PoS payload is checked before POST and the PMA
prompt+system+tools input is checked before its model call. Task history is
pre-trimmed with a 4,096-byte engineering margin, preserving the existing
native tool-pair rules; the final guard still rejects required overflow.
Existing max_tokens remains the output reservation. These byte checks are
not a tokenizer or proof of provider context-fit; actual token/cost parity is
unknown. No limit is imposed on original GA-only/U/PoS modes by this guard.

Typed stopping and known facts
------------------------------
Candidate-only required host journal failure closes the bridge before later
Task/auxiliary sends. A known executed tool result or CURRENT_TASK_DONE stays
the Task fact; auxiliary archive_incomplete/error remains distinct. PMA
per-operation malformed parameters retain the upstream per-item behavior;
fatal bank/capture failures propagate after retaining already committed
operations and skip Phase 2. PoS semantic rejection, format repair exhaustion,
and role transport failure have separate candidate outcomes. An accepted or
acceptance-unknown request is never re-sent by the spool. Original U and PoS
exception behavior is not retroactively changed. None of these checks gives
the auxiliary method a Task-completion veto or an evaluator approval role.
