Conclusion
----------
The two historical failures are Task calls, not PoS role calls. Each has one
observable HTTP attempt, HTTP 200, some parsed public content (the new sampler
has ordinary text), then the local incomplete-stream marker and a Task
PROVIDER_FAILURE terminal. The provider_response outcome=success event means
the parser generator returned to _stream_with_retry; it is NOT a certificate of
a complete answer. Neither underlying response Content-Type, first raw SSE
event time, raw message_stop/stop_reason, upstream request ID nor pre-parser
frames were saved. A missing terminal marker is a LOCAL PARSER OBSERVATION:
the historical source cannot prove whether an upstream server failed to send
it, a proxy/client interrupted it, or the parser ignored a frame.

from a parsed response. The exact Content-Type and upstream request ID remain
unknown. The local llm_call_id is not an upstream HTTP request ID.

Zero-network synthetic tests and a separate policy risk
-------------------------------------------------------
synthetic_test_output.txt records seven passing tests against the staged
Task llmcore.py parser/HTTP wrapper and GA classifier/loop, with requests.post
replaced by a local fake. Tests cover complete text+tool, text then EOF without
terminal frame, partial tool then EOF, explicit SSE error, max_tokens, malformed
JSON/multiline data, and actual GA loop dispatch. This demonstrates current
code behavior, NOT the historical network failure. The parser uses per-line
data: JSON, ignores non-data lines, prints-and-skips malformed JSON, and does
not reassemble multiline data fields. Without raw frames we cannot determine
whether any of these happened in the historical calls.

A substantive synthetic finding: a partial tool-use block can survive an
incomplete stream, and the GA loop dispatches that synthetic tool before its
final PROVIDER_FAILURE classification. The two historical failed calls had
zero parsed/selected tools, so there is no evidence of partial-tool execution
in those attempts. max_tokens is marked by the parser but is not recognized by
the same provider-error predicate. These are classification/dispatch policy
observations requiring separate change authorization; production behavior was
NOT modified under this diagnostic-only request.

Boundaries and next step
------------------------
The available data cannot choose among upstream truncation, proxy/client
interruption and parser frame loss. The smallest evidentiary next step is a
separately authorized, privacy-safe pre-parser event-metadata capture on FUTURE
runs (timestamp/type/length/hash/parse outcome/close reason; never raw hidden
thinking or credentials), plus an independently scoped decision on handling
partial tool blocks and max_tokens. Do not retry either historical call to
answer this question. All old scores, terminals and events remain unchanged.
