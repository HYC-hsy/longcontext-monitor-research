# 当前工作认识的请求级恢复：候选实现

用户批准检查与改造；完成后停在真实运行前。主体仍为独立Clean Monitor，服务A/B的认识维护与消费衔接，不是PMA改造或论文创新已成立。

## 设计与边界

原实现：working.md由模型自主写，后续自主读取或压缩交接时使用；普通推理没有可靠的最新笔记消费路径。

新候选：正常有工具推理前，读取同任务private目录的working.md，在本次请求尾部作为明确标注的私有认识提供。调用完成或异常时移除这一临时输入，不反复追加到持久History。此前实际写入和调查历史仍保留；不删除历史旧认知。压缩完成之后才读取，因此能立即看到新交接。维护调用本身不再额外注入，避免重复旧笔记。

强制保证的是请求级读取与清理；模型仍决定笔记内容、组织方式、何时更新、如何判断与何时行动。没有每轮写入门禁、固定ID/schema、新工具、第二维护模型或同步任务审批。笔记标注为可能过期的认识，不提升为system规则或公开事实。

最大展示8000字符，超出明确标注首段节选与完整文件回查路径，不限制文件大小。缺失/空白不注入，读取错误明确告知而非复用旧缓存。此上限是有界工程初值，不是经过效果优化的参数。每次实际提供的视图进入dialogue审计，增加磁盘记录但不递归进模型History。

## 与已有机制的关系

- working.md复用，没有新建平行bank。
- 同History及压缩交接保留；临时视图不持久堆叠，但历史已有旧笔记仍会出现，不能宣称彻底消除陈旧认识影响。
- U的原文引用恢复、A的选定调查恢复不替代本次私有认识读取，保持原开关；首轮候选比较不应将其一并开启。
- 当前不改synopsis、不改观察周期、不改提示中的领域规则、不自动验证笔记正确性。
- 没有修复“模型从不更新笔记”的全部问题：只是提供明确消费位置和说明，使自主更新有直接用途。是否会有效使用是实验问题。

## 开关与文件

默认关闭，模型配置 `monitor_active_working_context: true` 开启；GA适配 `GA_MONITOR_ACTIVE_WORKING_CONTEXT=1` 映射该配置，0关闭。未修改已有真实manifest或密钥。未来运行包必须包含新增核心模块并通过准备门禁，未自动启动。

- `monitor_agent_core/working_context.py`：有界读取、缺失/错误/节选处理。
- `monitor_agent_core/agent.py`：候选开关、模型可见说明、读取与审计回调。
- `monitor_agent_core/provider.py`：压缩后、请求级临时注入，finally恢复历史；重试复用该次快照，不重放工具。
- `ga_monitor_adapter.py`：单一布尔开关接线。
- `tests/test_monitor_working_context.py`：7项针对性检查。
