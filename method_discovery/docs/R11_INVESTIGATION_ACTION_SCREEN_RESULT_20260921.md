## 工程边界

选择观察已分为研究记录与模型可见观察。父 Supervisor 只看到工具名、真实参数、原始回执、冻结查询范围和版本；`candidate`、`caller`、run id 与实验条件名不进入父请求。生产请求级回归确认：只替换候选名称、保持动作及回执相同，实际父请求完全相同。

首次九份运行的第 4、5 项在任何模型请求发出前因重复轮次共用私有目录而触发 `FileExistsError`。原失败与零调用记录保留；修复路径身份后，只恢复这两项到独立输出。第 9 项是模型真实耗尽六次调用仍未裁决，未重跑。

## 结论

- A 没有产生收益信号：错误态仍 0/2，且把原本可正确批准的控制案例拖成错误未决。
- B 有一次父模型后续找到真实 JSON 反例，但首动作选错了调查对象；另一次仍错误批准，正确控制又耗尽预算。现有证据不能支持“短视图改善了动作选择”。
- A/B 都表现出“强制花一次调用选择动作”可能损害已充分支持状态的收敛；它们不是只变得更会发现错误，而是更容易偏离或不结束。
- 本轮不提升任何候选，不美化 selector，不开发 C/D。若以后重新考虑动作选择，首先要解释为何动作总落在完成声明、已修局部或文件清单，而非能改变根判断的未覆盖要求；这需要新的、独立批准的机制轮次。

逐记录机器可读评价见 `method_discovery/runs/r11_investigation_action_screen/evaluation.json`。公开提交仅包含安全结果、配置与报告；完整 History、工作区材料及 transport/audit 原文继续留在受控本地。
