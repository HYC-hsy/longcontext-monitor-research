# PMA强基线：源码核对与待确认调度选择

## 本阶段结论

本轮只做原仓库对照与设计，无API/真实任务/生产修改。发现不能把PMA直接塞进现有异步worker然后仍称保真复现。建议保留原生维护—提醒语义和同步调度，建立独立基线分支；主方法Clean Monitor继续并发，不将其退回逐轮审批。该建议涉及对照协议与同步执行例外，必须经用户确认才实现。

## 已核原代码（本地固定revision）

配置和_trigger_memory_agent注释写single-phase，但process实际调用两个phase，以执行代码为准。第一次只有任务信息；最近步骤窗口不包含那条重复的任务描述。step格式最多显式展示5个commands，超出部分给计数提示；终端输出继承任务端截断，不据此声称看无限原始日志。

原process对phase错误捕获后仍可能返回不注入：适配至少必须独立记录失败/部分成功，不能把传输故障计为正常静默。是否延续旧bank进入phase2应保留并记录，不无声升级策略。

## 为什么这个选择会影响论文

PMA同步意味着每一步都有维护机会，也意味着额外墙钟等待。若改成后台只消费最新8步，慢请求期间中间步骤可能永远未进入bank；这不是仅换一个运行容器。

保留PMA原调度的比较回答“完整系统在共同任务和资源政策下如何”；它不能单独证明我们的记忆表示更好，因为调度、工具调查和提醒角色也不同。核心机制解释必须依靠我们共同母体内的消融及简单替代，不靠外部方法对比承担全部因果归因。

## 建议的第一版（待用户确认）

1. 建立独立PMA基线入口，不改Clean Monitor普通并发路径，也不使用它的强制中断/完成批准机制冒充PMA。
2. 保留bank操作、两phase、窗口、同步逐步触发和一次性软提醒；初始化各题reset。不借用我们特有的主动工具调查、持续repair或终局checker。
3. 尽量使用共同任务Agent底座、公开输入、模型身份与离线隔离，明确GA步骤到PMA步骤的映射。模型/底座/题源不同于论文原设时，名称为“PMA机制保真适配（GA）”，不是原论文成绩复现。
4. 所有维护/提醒调用、等待、失败与计费纳入成本。固定任务机会和固定总预算实验分开；同步时间属于系统成本，不隐藏。
5. 同步行为仅限获批准的外部对照分支。主方法不得出现“监察挂起导致任务冻结”的架构回归。

不建议第一版同时维护同步、异步两个PMA实现。先做机制保真对照；若后续研究问题需要再加入异步版本，作为明确的调度消融，不能临时按成绩挑选更弱的PMA。
