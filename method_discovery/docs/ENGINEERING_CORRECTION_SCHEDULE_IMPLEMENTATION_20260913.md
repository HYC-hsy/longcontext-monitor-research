# 工程纠偏调度实现

## 本轮目标与边界

按用户已确认行为直接实现，不仅记录规划。开始版本a30a837，旧主动暂停工具已退役。无新模型工具、无新分类模型、无在线checker；不改变R2的信息视图、通用工具、持续history及隔离。实现和测试单步总改动低于600行；未调用API，未启动真实任务。

## 实际控制顺序

1. 普通观察仍并发。provider看到公开流事件明确选择既有intervene工具，即向宿主发送correction_begin；不扫描自然语言或隐藏思考关键词。
2. 尚未进入纠偏跟进期时，父进程开启工程barrier并请求GA取消当前推理/工具；任务循环在下一模型调用前等待，尚未执行的旧工具不继续执行。工具副作用不可承诺回滚，记录为取消请求，不假称已经物理停止。
3. 纠偏参数仍按原流协议验证。完整有效消息经现有中断邮箱提交后，finally释放barrier，任务以该用户式输入恢复。
4. 父进程进入focused状态。同一监察会话继续运行、读取当前工作认识/近期速览、主动查询原始材料。其后续模型调用及纠偏内容生成不阻塞任务；有效后续intervene仍通过现有中断接口立即送达。
5. 监察者选择wait时退出focused。下一次问题重新走首次停止路径。根完成原有独立等待保留，不增加逐轮审批。

模型若没有公开选择intervene，工程无法知道它已经发现问题。部分中转只在最终响应给出工具名称时，只能在最终解析/发送前触发。该边界不等于“在模型脑中发现问题的瞬间停止”。此轮不新增一个“发现问题”模型工具或结构化判断表。模型读取选择与真实跟进速度仍须真实任务验证。

## 工程文件

- provider.py：既有intervene的流式公告；异常/重试/下次请求前清理；没有修改工具参数或绕过流完整性检查。Responses/Anthropic/Chat路径均识别公开工具名称，最终解析为缺流头提供后备。
- runtime.py：跨进程begin/end接线、首次/跟进状态、送达后恢复、静默退出、失败和退出清理。300秒工程故障上限会记录correction_delivery_timeout，非模型可选暂停租约。
- correction_barrier.py：线程安全的工程等待点、身份匹配和最终超时保护。
- agentmain.py / agent_loop.py：原有取消能力、任务调用前等待、未执行工具取消，不重启任务或新建会话。
- agent.py：补充简短运行说明，告知直接intervene、宿主管理停止恢复、并行看最新响应，不要求脚本自行暂停。
- vendor与NOTICE：实际复制函数及来源边界。
