# U Fyne R1：原始轨迹审计与候选选择建议

## 范围与裁决

用户授权审计并考虑其他候选。本轮只读原始公开轨迹、监察工具参数/结果、续接笔记和代码，更新文档；未修改执行代码、调用模型API或重启任务。

核对全部28条intervene参数、唯一U调用、8份成功续接，以及重点局部修复/完成交叉时序。未重新执行整个工作区的测试，不把每条纠偏都判为正确。真实运行基本数据见RESULT报告。

结论：本轮不支持“U来源恢复机制有效”，但也不足以否定该思路。实际实现改变了可选工具目录，没有改变最常用的认识恢复路径。后段问题同时包含自主纠偏策略、观察陈旧和完成协议，不能一概解释成记忆遗忘或模型能力差。

## 1. U不常用：能确定的实现缺口

`provider.py::_compact_with_continuation`把新note直接写入carried History。模型通常无需再读working.md即可消费其中结论。`agent.py::GROUNDED_PROMPT`只是告诉它按需用read_with_sources；没有在这个实际消费点恢复来源。

实际调用：原任务普通读取6次、synopsis73次、public_events71次、普通working.md读取1次、U1次、code_run112次。故“只用一次U”不等于“不看原证据”：它大量主动读原日志和源码。不能为提高工具使用率强制再读同一笔记。

唯一U调用1788873354.303发生在初始化，读原题和最初事件，尚未检验后续认识变更时的来源复查。后续8份成功续接全部使用`/logs/...:行号`链接，而工具只展开`task/`、`monitor/`及`#L...`范围。U格式没有沿着笔记生成路径保持。没有第二次调用，因此这是已确认接口不一致，但不是已发生工具报错，更不是“不调用”的已证因果。

进一步限制：当前U只展开选定笔记前8个链接，既不能保证这些正是当前决策需要的来源，也不能判定链接支持其解释。当前笔记常链接synopsis，恢复导航文字仍不等于恢复实现行为。不能通过“有来源链接”宣称grounding已经成立。

**判定：U0是可用的工具候选，不是已完成的决策依据恢复机制。**

## 2. 不是只有坏结果：具体能力仍在

- App.Metadata缺失实现、URI Content占位、Bytes/反向格式化遗漏、Menu.Refresh只刷新首窗口、Toolbar构造路径未连接刷新等被指出，任务有对应修改。
- nil-driver托盘测试失败时，没有永久认定生产代码有错。1788875506识别`defer fyne.SetCurrentApp(test.NewApp())`参数立即求值影响CurrentApp，任务后来修正fixture并局部通过。
- 1788877074重新发现明确根要求：返回最后DataChanged对应的源错误。此前仅重读当前源不能满足。后续缓存序列测试得到加强。
- 续接笔记实际能写“此前menu问题已解决”“tray getter相关担忧只是hypothesis不是blocker”，因此不能说完全没有修订或释放能力。

限制：最初局部测试有noop也能通过的问题；晚发现缓存要求表明先前“七项目标已有证据”不够完整。保留根标题不等于保留每一项关键语义。

## 3. 局部循环的一个直接因果锚点

1. 1788875506监察者指出fixture问题。
2. 任务220轮（公开事件425）准备移除baseApp、使用stub，方向符合纠偏。
3. 1788875531监察者再次发送认可诊断/要求落实的intervene。
4. 事件426记录`[Cancelled before execution for monitor correction]`，该补丁未执行。
5. 1788875565监察者又因为补丁未执行要求继续修。

这一段不是任务拒绝修，也不是缺乏通用工具。重复的确认式消息经强制中断变成实际阻碍。强制中断本身符合用户架构；问题是此时有没有新错误需要打断。不能通过恢复逐轮审批解决，也不能仅按字符串去重（相同问题未解决时仍可能需要提醒）。

还存在并发陈旧：1788877685仍以base.Init编译错误解释未验证，而任务此前已修；同条消息包含有价值的缓存序列建议。这是混合质量提醒，不能整体算有效或无效。服务失败/重试延长了观察至动作时间，但不能证明全部陈旧都来自服务。

## 4. 完成控制：模型判断与工程动作没有连续对应

普通review `7573e8c1f96f46709a6072b031a7e587`从cursor494启动，读取结果已含cursor499的完成提议。1788876489调用allow_complete却被拒绝，因为本次review的completion_pending在入口固定为false。

随后1788876526真正的completion review `97c83f35d49241ae8b3a1397773af511`启动；模型1788876542调用wait(1)。运行时将其转为`Continue the task; no completion approval was issued.`；1788876548普通review又读到任务继续。

工程对应：`agent.py`在review入口设置completion_pending；`runtime.py`在completion且未提交且非allow_complete时，把wait转换为通用continue。这不是语义上新发现了任务缺陷。

不能自动沿用先前allow批准新状态：原提议可能已过期，后续可能有真实遗漏。本轮后来确实发现缓存要求，早先allow的意图不证明当时任务正确。

但需要让“当前可操作的完成提议”和“这次review入口类型”清楚区分，并明确wait到底是保持观察还是要求任务继续。建议单列生命周期设计确认，不通过超时自动批准、旧批准长期有效或暂停普通任务解决。此项会影响候选比较，应在下一真实分支前处理清楚。

## 5. 后段为何反复修文档

1788876141、6235先指出真实矛盾：报告仍说托盘未实现、全套通过。不是所有文档检查都是吹毛求疵。

其后任务不断新增/改写完成报告，监察者多次扫描全套报告中的no-regression、pre-existing、deadlock-safe及测试数。1788878620/9059即使局部缓存已释放，仍要求继续核对这些声明。到419轮仍在处理报告里的历史“BEFORE”示例。

**事实**：任务产生重复且不准确的报告，监察者持续把它们纳入修复；监察者没有明确命令创建每一份报告，不能把全部新增归因给它。原题主要要求功能/API与兼容性，没有要求维护这整套报告库。

**推断**：修复策略一直针对错误表述，未充分改变反复制造这些表述的任务行为；同时没有稳定区分当前交付结论、历史过程记录和剩余功能风险，导致局部纠正不断产生新的待查对象。

人工原始015/016提供不同处理：用准确起始版本、同环境的单个失败测试作对照，结果决定追查回归还是结束。自动28条提醒没有提出这种匹配基线控制；112次code_run中相关git show是查tag实现，不是同环境回归判别。不能保证增加这一次控制必然通过，但它比无限修改“是否pre-existing”的措辞更可能消除决策疑问。

同理，任意自定义DataItem重入是一种可构造风险，不等于已证明当前常用路径必然死锁；应区分纠正过强保证、证明根任务相关缺陷与可选强化，不能把所有可构造风险自动变成阻断。

## 6. 成本为何仍高

按dialogue tool_result的JSON序列化字符统计（不是token、也不是去重字数）：public_events约4,947,528，code_run约482,119，synopsis约473,289，原题约61,070。最大来源是原事件读取，并非U的19,796字符。

具体1788874167读取42行public_events产生132,815字符，其中20次`[WORKING MEMORY]`、21个next_prompt字段。每行事件可能包含任务Agent已经叠加过的工作记忆；连续原事件读取会再次带入这些内容，之后又通过监察History多次发送。

因此“主动读”“按行有界”都不等于低成本增量。不是外层偷偷每轮灌全量，也不是要删除原始日志：需要区分原始材料永久保存与当前问题需要消费的片段。这可成为后续U改造的方向，但本轮不据字符分布推算确定可节省百分比。

## 7. 是否试其他候选

|候选|本轮判断|下一次应判别的实际差异|
|---|---|---|
|U0：当前可选来源读取工具|不继续原样重跑；未证明独立收益，不淘汰来源恢复思想|需先说明如何进入真实消费路径，而非只新增目录里的工具|
|W：交接写入校验|保留为竞争候选，暂不优先|8次交接中能否捕捉具体语义丢失/升格；需要证明写入是主因，避免多一次重读却不改变行动|
|R：可修订的纠偏依据|建议下一机制优先考虑|收到任务响应后，实际修订自己的下一要求：继续执行、缩小、撤回、换取证方式，而不是只检查对方是否落实|

R原设计说“若需要U作载体，先比较U与U+R”。这里不能把未成立U默认为必要底座：可以使用已有同History和自然working note实现R，不要求新ID/schema；但需要先明确能观察到的状态维护/消费变化，不能只追加“请反思自己的建议”提示。是否实现仍待用户确认。

一个最小方向是把**仍在影响下一次干预的理由、任务对此的实际响应以及当前需要改变的决定**保留为同一份可编辑局部认识；下次消费的是更新后的理由，而不只是上次命令。模型自定内容和什么时候调查，不给每个unknown硬设次数，不让程序替它判语义。要验证它确实修订/撤回，而不是文档更完整。

目前不承诺唯一R接口；若最后只有prompt差异，必须如实叫prompt候选。先完成生命周期歧义的独立设计，再只引入一个可辨认机制。同题/同预算/同模型比较，不能同时加W、R和来源视图后把收益归因R。
