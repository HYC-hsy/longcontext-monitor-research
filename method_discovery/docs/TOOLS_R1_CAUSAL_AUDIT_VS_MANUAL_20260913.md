## 核心发现：监察者将当前行为当作恢复原题的依据，纠偏可能反而污染任务

### 1. 第7项：不是题目要求矛盾，是监察者虚构要求

原题明确只有desktop.App的SetSystemTrayMenu和SetSystemTrayIcon两个方法。没有driver.Desktop嵌入，也没有SupportsRunInBackground。
初始file_read完整返回178行、truncated=false；初始working.md只写“Define desktop.App interface in driver/desktop/app.go”，省略了两个具体方法。
任务95轮/cursor185先出现“Adding SupportsRunInBackground to driver.Desktop”。监察者1789284886的公开分析保留了任务这个错误功能，只认为应新建App接口；读取review_context(after_cursor184)后，1789284902断言“actual requirements”包含嵌入与新方法，并给出错误完整代码。
随后写进working.md为正确结构。105轮任务找不到接口欲删嵌入，监察者1789285010再次阻止，编造原题引文“embeds the existing driver.Desktop”。112轮任务决定创建原本不存在的driver包；113轮创建driver/driver.go，116轮恢复嵌入。监察者将此计为成功。
终止后测试显示desktop.App多了不应要求的方法（mockDesktopApp缺AbsolutePositionForObject）。该失败与多余嵌入有直接对应，不等于全部0分皆由此造成。

输入机制交互：相关review_context均无query，附带原任务前4500字符，不含末尾第7项；行为却包含错误SupportsRunInBackground。全程仅初始化一次直接读原题。原题仍在历史且工具可重新查，不能称“无法获得”；但当前视图有选择偏差。首次压缩continuation_started=1789285309，晚于两次错误纠偏；故压缩不是该错误首次产生原因。

### 2. Bytes：监察者亲自撤销用户要求

原题DataItem允许Bytes，要求格式化可读、反向Set报错。监察者1789284062先要求补Bytes等；1789284217看到旧库无Bytes后又明确指示删除，并说“requirement mentioned Bytes, but ... just handle ... actually available”。任务照办。此处不是任务不听话，是错误纠偏被成功执行。
人工004原文正相反：旧库缺类型不能覆盖新版本要求；保留能力，选择兼容最小实现/结构接口并加公开行为测试；让模型选择具体实现，不强制架构。人工先守住不变量，再允许自由恢复，而自动以编译通顺为新目标。

### 3. 调查不等于有判别力的调查

自动能查源码、搜索、构建；但大量观察落在函数/字段存在、编译通过。第6项94轮公开意图把NewAllStrings解释为“验证slice里的字符串非空”，95轮声称完成；监察者转入第7项，没有据原题“组合多个validator、返回首个错误”纠正这一语义替换。
人工原始107254/干预006指出非nil颜色断言能让忽略所有覆盖的实现通过；107276/107289实际读取具体测试行。干预014指出空Refresh也能通过指针/数量断言，改为观察真正调用。干预011区分Get数值更新与监听通知，并以Sscanf直接对照判定测试oracle，而不是遇失败就改生产代码。
差距不是要更多测试，而是选择能区分“真正履约”和“看起来完成”的观察。

### 4. 连续跟进已经存在，但它在确认服从自己而非符合原题

自动工具28次order、26次after_cursor，能够追踪修改；原题被错误解释后，后续动作越服从，working.md越确信COMPLETE/所有纠偏成功。第7项的“错误意图及时中断”能力确实被激活，但执行的是错误目标。不能只加密唤醒或继续强调持续跟随。
人工同样会维持局部循环，但纠正后继续检验依据：合法0000与错误哨兵、URI注册后不能删除URI要求、测试同步失败不能直接改队列。它会给恢复方向，也会限定已经证明的部分，不把服从等同成功。

### 5. 普通醒来取消与验证过程相互干扰

自动114/115轮工具执行前取消；117/118/120/121轮code_run返回-9与用户强制终止。任务由全量build退到小范围build，再到语法/文件检查，最终122轮写总结。监察者期间连续wait1/2后再wake。
实现agentmain.begin_monitor_correction无条件追加code_stop_signal并取消模型；end只解除barrier，下一wait_monitor_correction才clear信号。记录与机制支持“唤醒取消干扰验证”；尚未用独立调度重放区分每次取消是在执行中遇新wake，还是信号清理窗口问题，不把所有原因锁死为频率。
人工普通tail/读取不会自动停止任务；有具体纠偏才中断。人工在监听测试调查时允许合理推进，在准确起始版本复现旧失败后停止扩大检查。当前方案“醒来就停”是用户批准的工程顺序，但频繁醒来有实际代价；不能偷偷改回另一种架构。

### 6. 最后不是没发现异常，而是给异常找了完成理由

自动1789285377认为持续中断属于external termination而非代码问题，宣称全部完成——中断不能证明代码没有问题。最终读取241后，确实识别了报告API名错误，并code_run grep实际函数/字段；随后称IMPLEMENTATION correct并allow。应修正此前“没有核对总结”的粗略说法：它核对过，只核对了符号存在性。
人工也容许报告措辞不完美，但那时已有具体行为测试；必要时只改报告而不重开实现。因此不能制定“最终报告错一个名字就不许完成”的新硬规则。

## 保留的正向能力

同会话、状态编辑、顺序读取与执行会话可用；能纠正Toolbar错误功能、nil-safe Add遗漏、编译常量错误；能在错误意图公开时介入。不是所有工具与能力都失败。没有证据证明新工具接口故障造成0分，也没有严格消融证明工具改善或退化。

## 结论与建议（未实施）

主因优先级：原题依据被当前解释替代、将服从/符号存在/编译当成功、唤醒取消妨碍获得验证证据。三个问题互相加强，不是单一“提示不够长”。
已授权提示策略方向应先解决：具体纠偏与完成判断回到原始依据；原树缺能力不自动删要求；调查观察能否反驳当前结论；发现环境不支持自己建议时重审建议。保留自由工具，不加领域规则或每次必填证据表。
调度/信号问题单独需要工程定因；不把改提示词当成清理信号的保证。下一步先做无API最小调度重放（若用户授权），再按原本授权准备提示候选；真实启动另确认。当前没有修改。
