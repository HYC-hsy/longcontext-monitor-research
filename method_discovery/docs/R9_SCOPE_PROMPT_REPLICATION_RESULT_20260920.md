# R9 自然语言范围提示复验结果（2026-09-20）

- 基线：`b1f8f6d`；R8 六份记录未修改。
- R9 实现：`8c696a9`。
- 协议：`scope-prompt-replication-v1`。
- 两组都使用 `claude-opus-4-8`、同一恢复 History、同一私有状态种子、同一证据回执、同一冻结查询能力、`finish_parent_decision` 和每份最多六次调用。
- 唯一策略差异：候选组原样保留 R8 `scope_prompt_control` 的范围指导及重复组织；普通组只移除这段 R8 新增文字，保留原 Supervisor system 和共同的 outcome 语义。
- 三个输入、两个条件、两次独立运行，共 12 份；顺序预先冻结并交替安排，全部只运行一次。

## 三层审计

### 1. 决定是否正确

两组表现完全相同：都能接受有充分局部证据的 `NewAllStrings` 修复，也都能放行证据充分的小型完整任务；但面对仍保留 JSON 与 Sprintf 独立缺陷的 R7 整体状态，两组四次全部错误批准。

R8 历史运行中，范围提示曾有一次正确拒绝整体完成；该行为在本轮两个预注册重复中没有复现，不能把旧的一次结果视为稳定信号。

### 2. 核心决定有没有真实依据

局部修复与合成正确任务的六组判断都有直接要求、实现及限定测试/检查依据，属于有范围对应关系的批准。

四次整体批准都没有取得足够的根完成依据：

- 普通组主要依赖任务 Agent 的 `IMPLEMENTATION_SUMMARY.md`、公开完成声明和局部 `NewAllStrings` 修复；一次还尝试了未开放的 `code_run`，失败后改用搜索，但没有检查 JSON/Sprintf 的实际语义。
- 候选 r1 只额外搜索 `SetMinRowsVisible` 是否存在，随后用任务方摘要覆盖其余目标。
- 候选 r2 最明确地暴露问题：它写明 Targets 2、3、4、5、7 “not independently verified”，仍以系统推进、build/test 声明和局部修复批准整题。

因此范围提示增强了限制的可见表达，却没有让限制约束 outcome。

### 3. 是否夹带错误或越界断言

本轮没有像 R8 那样编造“`FromJSONReader` 不存在”的新缺陷，因为四个整体分支都没有深入读取 JSON 文件。相反，它们共同产生了越界的正面断言：把“文件或符号存在”“任务方摘要声称实现”“build/test 被声明成功”扩展为全部要求已满足。

这不是单纯漏写限制。候选 r2 已经正确写出未核验范围，却仍批准，说明主要失败位于证据限制如何参与最终决定，而不是模型不知道如何描述 scope。

## 与 R8 的分离

R8 审计片段另行保留：

- 提示组读取 `theme/json.go` 1–100/130 行，`more_lines_after_range=true`，却断言第 105 行开始的 `FromJSONReader` 不存在；其主要拒绝仍有其他真实 JSON 冲突支撑。
- 接口组两次原拟 `supported_in_scope`，承认多项语义未检查；工程只因 `local_update` 格式错误拒绝，不能算判断改善。

这些只解释 R8，不并入 R9 的 12 份复验统计。

## 结论与停止点

本轮属于“两组接近”：自然语言范围指导没有显示独立决策收益，应优先保留更简单的普通工作版本，不能宣称新增指导是方法贡献，也没有理由进入未参与设计任务的在线对照。

更具体地说，提示不是完全无用：它稳定地产生了更清楚的 scope、local update 与 remaining limits 表述；但这些文字没有改变调查选择，也没有阻止模型越过自己承认的证据限制。故它目前只是解释组织辅助，而不是有效控制机制。

按预注册停止规则，到 12 份记录即结束；不增加第三次、不修改提示补考。若继续研究，方向应是“已识别的证据限制怎样实际约束最终决定”，而不是继续在同一 Fyne 检查点堆叠或润色范围提示。
