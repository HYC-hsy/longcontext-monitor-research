# 增量记忆工作区与少工具接口：下一阶段设计 v1

## 状态与目标

**这是供用户审计的设计，不是已实现、已验收或已授权运行的新版本。** 当前开发线程继续既定的必要补修和一次真实 SQLite 诊断，本文件不改变其任务、启动授权或代码。

设计依据为当前状态化记忆源码及连续修复提交 `397b36a8c324c89c11621daa738fc30861c2668b`。后续实现应重新对齐届时开发主分支，而非覆盖它的预算和宿主补修。

目标：模型只表达新增或修改的记忆内容；程序负责保留其余草稿、精确引用、版本和发布。减少重写与机械字段，不减少必要的证据和语义审核。

分成两个可独立比较的改动：

1. 增量编辑：用局部修订修改同轮草稿，替代完整提案重写。可先沿用结构化文本响应，不依赖工具调用。
2. 工具化：相同修订内容通过现有模型工具通道提交，不再要求模型在普通正文中包装完整协议。

不保证天然优于现方案；是否值得启用，要结合当前真实轨迹和后续对照。两者都不加入新模型角色，不恢复人为输入硬门槛。

## 一、仍然是一份逻辑记忆

底表继续维护现有内容：任务要求解释、事实、经历与经验、实体关系、信息/成就缺口、关注点，以及范围、来源和历史关系。

程序内部持有：冻结正式版本 B0、本轮累计修订意图、当前私有草稿 D、准确的审核绑定。它们是同一份记忆的事务状态，不是多个独立 memory bank。

- 整理者修改草稿；审核通过前不改正式记忆。
- 审核者看修改前后工作集、diff、原始证据和必要未改对象。
- 选择者只读取已提交版本。
- 审核意见进入本轮反馈和运行留证，不成为另一份长期事实库。

工作集外未修改的记录保留，但不冒称本轮已全部审过。继续保留 reviewed_this_cycle / not_reviewed_this_cycle 区分。

## 二、三个角色各自只暴露一个工具

| 角色 | 唯一工具 | 核心输入 |
|---|---|---|
| 整理者 | `edit_memory(changes, undo=[])` | 哪些记录的哪些语义内容要变；可选撤销本轮修改 |
| 审核者 | `review_memory(outcome, issues=[], closures=[], reason=null)` | 判断、问题、关闭依据评估、无法审核的原因 |
| 选择者 | `choose_reminder(note, refs=[])` | 提醒内容和已提交引用；note=null 表示明确静默 |

每个角色只看到自己那个工具，不同时选择三个工具。没有 13 个业务动词，没有独立 diff 工具、focus 工具或 no-change 工具。diff 和审核视图由程序直接准备。

原生工具仍有结构化参数；不是“完全不需要格式”。主要去掉模型填写的协议名、hash、请求 ID、版本、绑定清单、存储偏移及重复正文。

## 三、整理工具的明确合同

```text
Revision = {
  changes: [
    {
      target: ExistingHandle | {new: LocalAlias, kind: RecordKind},
      values: SemanticPatch,
      basis?: {reason: Text, evidence: [EvidenceSelection]}
    }
  ],
  undo?: [ExistingHandle | LocalAlias]
}
```

ExistingHandle 是程序展示的短句柄，例如 K1、G2、F；不是模糊名称匹配。新对象显式声明本轮别名及类别。类别表示同一底表里的实体、状态、关系、要求、缺口，不是另一套操作枚举。事实/经历是状态的语义分型。

### 修改语义

- 未出现的记录和字段：保留当前草稿中的值，不是恢复 B0。
- 对象字段：按已知 schema 递归合并。
- 列表：提供时整体替换，不按文字猜测要删哪个元素。
- null：只在允许为空的语义位置生效，例如 lesson、closure；不是通用删除符。
- 新记录：必须提供该类所需的语义内容。仅可为“未提供可选项”填确定默认值，不能替模型猜范围、来源性质或关闭依据。
- 同批重复目标、未知字段、越权字段或悬空引用：整批不生效，不先写一半。
- 状态的知识/经历分型切换，若既有合同允许，须明确新分型及完整分支内容，由程序确定性移除不兼容字段；不能因普通字段省略而悄悄删内容。
- 身份类别不能改变，例如不能把一个实体句柄解释为缺口。

### undo 与撤回事实严格分开

- `undo=[K1]`：撤销 K1 在本轮的全部修改，恢复 B0 中该记录；若是本轮新建对象，则取消这次新建。
- `changes=[{target:K1, values:{use_status:retracted}, basis:...}]`：对已经保存的记忆作语义撤回，保留历史并接受审核。
- 不提到前一次修改，绝不等于撤销它。
- undo 不自动级联删除其他记录；需要同时修正依赖，否则整批拒绝。
- 取消新对象后，其别名在本轮保留墓碑，不重新用于另一对象。
- `changes=[]` 表示明确提交当前草稿，不必然表示与 B0 相同；缺少输出/工具调用不是 no-change。

### 关注点也是底表记录

F 的普通修改包含目标缺口和原因。明确清空 F 使用 `values=null` 加清空原因；`undo=[F]` 则恢复 B0 的关注点。这两个操作不同。其他记录不允许用 values=null 物理删除。

### 引用规则

程序展示精确引用句柄，区分：B0 中的版本、结果草稿中的版本、只读历史版本。建议记号 `b:K1`、`d:K1`、`h:H1`；这些记号必须实际由程序发放，不能凭前缀自行构造权限。

- `b:K1` 不会因为 K1 被修改而自动升级到新版本。
- `d:K1` 明确指本批结果草稿中的对应版本；同批前向引用先登记再统一解析。
- 新建别名在本轮保持同一身份，不能每修一次生成新记录。
- 历史记录只读；看到它不代表允许修改它。
- 来源句柄若仅指一大段文本，仍需给选中引文；只有指向准确可见片段的句柄才可以省略再次抄写引文。
- 继承的旧引用保留原精确版本和原始片段，不全局改指最新头。

## 四、模型和 Python 各自负责什么

模型仍负责：

| 内容 | 不可由程序猜测的部分 |
|---|---|
| 事实 | 说了什么、观察/转述/推断、当前/历史含义、支持与反对依据 |
| 范围 | 适用对象、前提条件，不能把本 shell 成功推广到新进程 |
| 经历/经验 | 条件、实际动作、结果，以及可选经验；经验不等于已观察事实 |
| 要求 | 对用户要求的解释及原始依据；退役/替代的真实理由 |
| 缺口 | 类别、目标、关联要求、状态、关闭或重开的依据 |
| 关系/关注点 | 关联对象、关系含义、证成依据、该关注哪一项 |

Python 负责稳定 ID、直接前驱、版本加法、任务/周期绑定、存储来源偏移、精确查找和校验、工作区差异、提交身份和事务。

经历固定为过去经历、经验固定为推断等由类型定义唯一确定的标签，可由程序填写。普通事实的来源性质和时序不能仅从工具输出类型猜。工具 stdout 里也可能是 Agent 自己打印的总结。

改文本时没有显式改依据，可以保留原依据，但“保留”不等于“新陈述已获证明”；审核必须重新判断是否足够。额外的语义 supersedes 关系不能当作纯版本元数据删掉。

事实发生时间与写入时间分开。程序不能拿 event_seq、ga_turn 或最大来源序号随意替代发生时间；现有元数据语义须在兼容映射中保留。

## 五、一轮完整流程

1. 冻结 B0、有效任务版本、观察连续前缀、工作集、可编辑对象和来源窗口。
2. 整理者得到相关完整底表、要求、实际动作、新/未合并观察和来源。初次输入不是 diff-only。
3. 模型提交 changes；程序在临时副本上合并，校验整批和全体候选结构，成功后才替换私有草稿。
4. 程序自动生成 before/latest-draft 审核视图及 diff。审核覆盖范围内的保留旧内容，不只覆盖 changes。
5. 审核有合法问题时，同轮保留整理者真实上下文及实际输出，追加紧凑回执和审核意见。
6. 整理者只改受影响记录；此前无关修改自动保留。程序重新构造候选和审核绑定，再审准确的新草稿。
7. 只有新草稿通过后才 CAS 提交，再由选择者决定提醒或静默。
8. 下一轮从正式记忆重建上下文，不无限继承所有历史修复对话。

保持现有修复次数和角色数，不另加格式转换 LLM、独立裁判或回显清单。

## 六、如何接回现有实现，而不是重造整套系统

新增的是“累计局部修改 → 完整内部候选”的适配层，不替换 CycleEngine 控制顺序或 MemoryStore。

建议内部接口：

```text
open_workspace(base, goals, workset, sources, host_binding) -> Workspace
apply_revision(workspace, revision, expected_draft, call_identity) -> Receipt
compile_candidate(workspace) -> CandidateUpdate
prepare_review(workspace) -> BoundReviewView
publish(workspace, validated_review, store) -> CommitReceipt
```

expected_draft、call_identity 等来自程序已发出的请求，不要求模型回显。单独调用内部 API 的客户端仍必须传这些绑定，不能靠全局变量猜。

所有修订相对同一个冻结 B0 编译：正式 state_version 只加一次；旧记录持久 revision 按 B0 加一次；新记录始终 revision=1。草稿序号单独记录，修复多次不制造多次正式历史。

优先复用：SourceCatalog、来源精确校验、validate_snapshot、历史归档、AuditCodec、project_snapshot、工作集和 BM25、提醒校验/投递、compare_and_swap。

必须适配：候选编译、内部操作索引、关闭清单和短句柄映射。不能声称直接调用旧 build_candidate 就已经覆盖全部情况。

### 兼容性必须闭合的具体点

1. **内容与状态同时改变。** 旧完整 upsert 可以带新状态，但旧 record_transition 的理由/证据另存。增量编译不能丢掉显式 basis，也不能对同一对象重复执行 upsert 与 transition。应生成一次记录更新及经验证的变更说明，确保理由进入审核绑定和提交留证。现有 store 对某些恢复为 active 的说明校验需明确适配，不能静默扔掉理由。
2. **缺口根据 B0→最终草稿判断。** 草稿里先关再开，若 B0 本来开放，不得虚构两次持久生命周期。已有关闭的缺口重开与撤销草稿关闭不能混淆。
3. **现有合同本来禁止的组合不偷偷开放。** 新建即关闭、已关闭缺口直接重写成另一关闭状态不能机械套用旧三个 gap 操作。若要开放，必须单独定义重新证成和审核规则；初版不借接口变化顺带开放。
4. **重开依据。** 原结构主要用 gap.reason/关联记录表达，并没有完整独立的重开依据历史。适配器须使输入 basis 在审核中可见并有对应留证，不能收了证据却在编译时丢失。
5. **继承来源重新编码。** 旧存储 SourceRef 不可直接塞进模型提案。程序应在冻结窗口内做无损转换；准备可编辑视图时就确认需要的旧片段可被保留，不到应用时才发现无法保留必需来源。不得借此扩大到不可见全文。
6. **要求与版本。** 活跃要求、退役要求、开放缺口和历史引用的 task_version 规则不同，不能统一盖上当前版本。修改要求/缺口后，受影响依赖须明确修正，不能自动升级所有旧引用。

既有完整提案能够合法表达的变化，适配器必须覆盖，不能以 unsupported 代替完工。上述兼容点未闭合前，只能称开发中的组件，不能接入真实运行冒充成熟替代品。

## 七、审核和选择接口减掉什么

审核保留当前三态、合法问题、关闭判定、实际依据和无法审核原因。程序注入协议与准确绑定，为问题分配 ID，并从当前关闭清单解析既知 before/after 身份。模型不再抄 coverage、hash、版本清单。

问题仍包含类型、目标/字段、解释、实际依据及必要修复约束。若关闭判定需引用某个问题，模型给自己本次提出的问题一个局部别名，程序再统一映射正式 ID；不能靠目标相似猜哪个问题阻断哪个关闭。关闭项仍明确给出 verdict、assessed_scope、explanation、basis 和相关问题别名，不能把程序填回既知身份误当作替模型作出了判断。

关闭条目的真实判断、适用范围及证据仍由模型提供；程序不能从“它引用了某条回执”推导 supported。合法与非法问题混合时不能过滤成 clean。没有返回问题也不等于已经明确提交 clean。

选择工具：`note=null, refs=[]` 是显式 silent；非空 note 需要当前已提交选择视图内的 1–3 条引用。没有调用、无效引用或不完整响应不等于 silent。保留现有提醒来源标签及投递去重。

## 八、真实 SQLite 现场的增量修复示例

来源：已公开运行 `pma-6632777c561a4f88` 第四个状态周期的维护/审核交互。下面 K1 是设计中的短句柄；修正文本和工具调用是设计示例，不是实际模型已经输出过的结果。

候选 K1 的真实原断言同时提到 configure、Makefile.in、autosetup/、src/、test/、ext/，但其支持引文只有：

```text
-rwxr-xr-x  1 nobody root    146 Jul 30  2025 configure
```

审核指出“单条引文只覆盖 configure，未覆盖其他组件”。一种保守修复是缩小陈述，不宣称完整构建系统已经验证。

整理者只需提交：

```json
{
  "changes": [
    {
      "target": "K1",
      "values": {
        "claim": {
          "text": "目录列表显示存在名为 configure 的文件，大小为 146 字节。"
        }
      }
    }
  ]
}
```

程序保留 K1 的原有效引文、范围、相关实体、本轮其他修改；不要求重写整份提案，也不把所有旧状态再传一遍。重新编译后审核者仍看到原观察、完整的相关候选、未改记录和 diff。是否确实足够仍由复审判断；不能预先把该例记成 clean。

另一条路径是扩大合法引文以支持原陈述，必须从本轮可见原文明确选择，不允许程序自动找相似文字凑证据。

## 九、原生工具传输的工程要求

- 复用已有 GA/模型传输，不另写客户端或增加格式化模型。
- 接收并保存真正的 tool call、参数、调用 ID 和完成状态；不是继续丢弃工具块只读取 text。
- 本轮对话保持真实 assistant 工具调用及对应 tool_result，不能伪造工具调用或把审核回复当作整理者输出。
- 工具回执只给草稿是否有效、变化摘要、必要句柄和具体错误；不无条件返回完整候选。草稿有效不等于已通过审核。
- 每个角色一次提交，整理批内可含多条修改；遇到多次/未知/截断调用必须按明确合同处理，不能只执行第一个后冒充完整。
- 同一调用重复到达不能重复应用或生成新对象；同 ID 不同内容拒绝，未知执行结果先对账。
- 拒答、普通格式错误、来源错误、审核 issues 和传输失败分开；保留原有有限修复规则，不因工具化新增无限循环。
- 不假定中转服务支持 strict 或强制工具选择，必须检查最终真实生效的请求。不存在工具调用不能悄悄当作静默成功。
- 有效 JSON 不代表正确记忆，工具参数也不能免除来源与语义检查。

## 十、当前结论

设计方向是：**同一底表，局部编辑；程序合并和管理身份；审核独立且看完整必要依据；正式提交后再选择提醒。**

本阶段只发布设计和验收标准，不改运行代码、不启用新工具、不启动模型。下一步先由用户审计；随后在独立分支实现增量适配，再用同一适配比较文本与原生工具传输。
