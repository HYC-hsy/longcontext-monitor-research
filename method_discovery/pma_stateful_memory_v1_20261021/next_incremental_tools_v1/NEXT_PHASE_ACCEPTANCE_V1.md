## 4. 必须覆盖的离线反例

| 编号 | 必须证明的行为 |
|---|---|
| E1 | 第二次只改 K1，第一次对 K2 的合法修改仍保留 |
| E2 | 同一新别名多次修订只生成一个对象，正式 revision 不随草稿次数增长 |
| E3 | 同批前向引用可解析；未知、跨类型、冲突或越权引用整批拒绝 |
| E4 | 省略、空列表、null、undo、语义撤回各自含义明确，互不冒充 |
| E5 | undo 新记录后存在依赖时整批回滚；不得静默级联删除其他记忆 |
| E6 | 修改未曾进入提案的可见旧记录可行，不能只支持修复新建对象 |
| E7 | 继承旧来源与历史引用保持精确；失败事务不扩充来源权限或泄漏别名 |
| E8 | 状态内容与可用性同时修改时，正文、理由和依据完整进入审核/留证，不重复加版本 |
| E9 | 草稿关后重开按 B0→最终结果归一化；已提交关闭的重开不是 undo |
| E10 | 要求退役、目标 epoch、关联开放缺口、关系锚点和关注点正确处理，不统一改指最新版本 |
| E11 | 原合同禁止的生命周期组合保持明确规则；原合同合法的组合不得变成适配器未实现 |
| E12 | 只改理由/依据但候选正文相同，也不能复用旧审核批准 |
| E13 | 任一字段、来源或整体验证失败，草稿、别名、正式状态与 frontier 均无半批修改 |
| E14 | 并发 B0/任务变化导致 CAS 冲突时，不自动重基后复用旧审核 |
| E15 | 有待处理观察但语义 no-op，不等于无须审核或无须明确推进 frontier |
| E16 | 目标 epoch 刚变化时，不能要求尚未整理的初始空草稿已经合法，导致整理者无法开始工作 |
| T1 | 保留真实 tool call 和匹配的 tool_result，下一次整理请求不是伪造 assistant JSON |
| T2 | 未调用、未知调用、多调用、拒答、截断和参数错误分别识别，不伪装成 no-change/silent |
| T3 | 同调用 ID 同内容不重复执行；同 ID 不同内容拒绝；未知传输结果不盲重发 |
| T4 | 工具回执明确“草稿有效”与“已审核提交”的区别，不声称未执行的状态已生效 |
| T5 | 审核混合非法问题不能过滤为 clean；缺关闭判定不能由程序自动补 supported |
| T6 | 提醒只引用已提交选择视图，不能引用草稿或别的周期对象 |

如果只完成其中一部分，应报告为未完成适配，不能以“工具能调用”宣布成熟可用。

## 5. 对照拆分与评价

保留三个明确条件，尽量使用相同任务依据、工作集、审核语义和修复次数：

- A：当前连续上下文 + 完整提案替换。
- B：增量编辑 + 结构化文本提交。
- C：与 B 完全相同的增量内容 + 原生工具提交。

A→B 观察增量表示及宿主代管元数据的收益；B→C 才观察工具传输本身的影响。若工具模式静默回退到文本，必须单独记录，不能仍称纯 C。

记录真实总输入（含 schema、历史、回执）、输出、修复次数、格式/参数/引用错误率、修复成功率、耗时、正式提交、提醒送达和 Task 结果。不能只比较工具数量或一段 payload 字符数。

语义反例包括：错误关闭、推断升级为当前事实、未改旧主张被遗漏、无关合法修改丢失、重复新对象、过时审核被采纳、弱自写测试被当作完整验证。程序正确应用修改与模型选择正确修改分开统计。

若增量编辑明显丢失合法修改、依赖错误增多，或总输入/修复负担增加而没有质量收益，不直接上线。若 B 有收益而 C 没有，保留增量编辑即可，不为工具化而工具化。
