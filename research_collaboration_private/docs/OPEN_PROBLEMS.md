# 请专家重点批评的地方

以下不都是确定根因。我们希望得到竞争解释，而不是为当前架构寻找合理化叙事。

## 1. 记住要求却不使用要求

R8 的最终 bank 仍记着 Sprintf 反向写入等行为要求；实际最后只查修过的 API 签名和 build，随后批准全部完成。事实是检查范围不足；“近期局部问题占据注意力”是解释假设，尚非因果结论。

疑问：问题主要在记忆表示、检索/消费、调查目标的形成，还是最终结论的校准？如何用最小机制区分它们，而非继续加提示词？

## 2. 两阶段维护与自主控制存在摩擦

R8 中维护阶段三次尝试 intervene 被拒绝，进入判断阶段后才成功。另有六次 wait 不可用。维护与判断的责任分离有价值，但模型已经形成可行动判断时，阶段约束反而浪费调用。

疑问：保留先更新后判断的核心联系，是否必须硬分两个工具阶段？应怎样衔接才能既不丢维护又不限制智能？此处未预定解决方案。

## 3. 局部持续纠偏与全局完成相互挤压

旧运行曾出现局部验证反复、超时；较新运行能退出，却在局部修好后轻率结束全局。不能简单选择“多验证”或“少验证”。人工参考能追踪误解、判断测试是否有区分力，再返回其他根要求；但人工具有先验知识，不能当公平自动基线。

疑问：是否需要可修订的判断依据，而不是越来越绿的完成清单？怎样避免它变成强制填表和另一套注意力负担？

## 4. 测试本身是需要审查的任务解释

build、方法存在、自写测试 PASS 都不自动证明原行为。R8 没有主动展开测试断言；人工参考 014 指出空 Refresh 也能通过原断言。反过来，测试失败也不总是生产实现错误，可能是 oracle 或环境问题。

疑问：如何促使模型选择真正有判别力的观察，同时不强制每个 unknown 都写测试？如何记录支持范围而不发展成在线 gold checker？

## 5. 压缩、缓存和成本

R8 压缩笔记把七项目标概括成已经实现，剩余工作主要是修编译；完整要求仍在 bank。压缩可能强化局部视角，但无对应消融。监察者记录 69 次模型用量，cache creation 累计超过 650 万 token；这不是唯一上下文长度或美元费用。两阶段 system 变化是否影响缓存命中需继续核实。

疑问：持久会话与更新后的 bank 是否形成重复或冲突？怎样保持认识连续而不重复发送大量材料？先可靠再降本与成本贯穿应怎样平衡？

## 6. 对研究流程的自我批评

我们曾多次追逐局部工程故障与提示修补；工程回归通过并不意味着模型会正确使用机制。候选越来越复杂也不代表贡献更强。不同题、模型、预算的历史成绩一度容易被误读为横向对照，现明确禁止这种推论。

专家可以建议删除机制、重新安排基线和实验，而非只提出增量补丁。最需要的不是再加几个理论术语，而是一个可证伪的核心解释和能区分解释的实验。
