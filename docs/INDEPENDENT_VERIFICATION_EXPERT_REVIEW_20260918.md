# 独立核验能力：专家审阅入口（2026-09-18）

这是方法发现中的局部原型，**不是在线监察机制，也不是论文效果结果**。本轮只试验：父监察者对一个具体要求产生疑问时，短暂新会话是否比同一上下文的普通复核更能独立判断；预先写下正确行为预期是否在相同额外调用上限内有增益。

## 建议阅读顺序

1. [核验实现](../src/monitor_agent_core/probe.py)及[原子单元测试](../tests/test_monitor_independent_probe.py)：C 为直接隔离核验，D 为先读要求、提交预期、再开放实现证据。它们复用现有 provider、`run_review` 和文件读取；不接入在线控制，也不能 `intervene`、`wait` 或 `allow_complete`。
2. [检查点配置](../method_discovery/artifacts/independent_verification_20260918/checkpoint_config.json)和[材料重建器](../method_discovery/materialize_independent_probe.py)：A 是归档的根完成判断，B 复制父 History 再普通复核，C/D 使用空 History。隐藏评分字段不会进入模型输入。配置中的判断标签是离线评估材料，**不能用于在线提示或任务执行**。
3. [面板运行器](../method_discovery/run_independent_probe_panel.py)、[测试](../tests/test_independent_probe_checkpoints.py)及[试跑审计](INDEPENDENT_VERIFICATION_PILOT_AUDIT_20260918.md)。运行器依赖原开发工作区中的任务副本与运行归档；本公开审阅包不含原始父 History、重建后的完整工作区、密钥和未筛选日志，故不能直接复现模型调用。

## 已知边界与待审问题

- 目前 11 个局部问题都来自 Fyne 2.2 同一个 turn-60 根完成检查点，**不是** 11 个独立时间检查点。能否用这批材料仅做协议校准？正式比较还应补哪些正确、错误、证据不足的独立检查点？
- Toolbar 的原题要求 `SetIcon` 更新字段并刷新工具栏，公开实现只赋字段；任务原生测试通过，但未覆盖刷新。应以原题行为要求为标签，还是将此项标为有争议、暂不计分？请指出支持判断的公开证据边界。
- B 的完整父 History 约 489k 字符，单个早期试跑累计约 586k tokens（含缓存读写）；C/D 在相同请求数上限下明显便宜。主比较应控制额外请求数、总 token、可见信息量，还是分别报告这些轴？缩短 B History 会改变“同一上下文复核”的含义。
- D 的预期阶段确由输入权限隔离，而非只靠“忽略旧结论”提示；但多阶段可能天然提高观察次数。六次请求、八轮上限是否足以形成公平、可解释的 C/D 对照？
- A 是根完成隐含放行，不是逐要求的显式判定；如何报告或替换 A，避免把它算成与 B/C/D 完全等价的局部 verdict？
- build-only 旧问题存在语义歧义，已改写，旧 D 结果排除。审计记录中的小样本结果只能用于诊断协议和标签，不能选出获胜机制。

## 当前可核对的结论

工程回归（独立原型、材料边界、provider/core）在原工作区为 63 项通过；不等于在线有效。JSON API 的 C/D 均发现缺口；Toolbar 的 C/D 分歧表明预期先行可能有帮助，但也可能是标签和额外观察次数造成；build-only 旧题无效。下一步应先解决标签与预算、增加独立检查点，再冻结面板作逐案比较。如果 C 与 D 相近，应保留简单的 C；若都不优于普通复核，应定位任务理解、取证或证据解释问题，而不是叠加新模块。
