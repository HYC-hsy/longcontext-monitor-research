# Fixed requirement attributes: isolated A prototype

Base: `b831347b4aff9e2802eb3478303ce4af5d0660bf`.
Candidate: `requirement-attributes-v1`, branch `pma/requirement-attributes-v1`.
This is P1-only. It does not connect Task, P2 or native evaluation and does not migrate old banks.

## Startup and cost

The same P1 client makes one separate startup call, with only the verbatim original task and the single `requirements_initialize(requirements)` tool. It extracts what ultimately needs to be achieved, retaining constraints. It separates final conditions from suggested execution steps and historical facts. There is no second model or reviewer. Startup does not receive Actor events, advance event presentation, or replace maintenance. After host validation and freezing, the first ordinary maintenance runs with those accepted text choices in its schema and prompt.

This costs **one additional logical P1 call per successful task initialization**, rather than claiming same-response zero cost. The first successful cycle allows up to 4 logical calls (1 startup + 3 maintenance); later cycles allow up to 3. Every explicit failed-startup retry is another attempted startup call and is recorded. Provider retry count/cost remains inherited and unknown unless the existing client exposes it; usage exposed by the client is retained. Maintenance keeps 4 total reads, only r0/r1 for serial discovery/following, and r2 write-only. No initialization tool is appended to that six-tool list.

The catalog may explicitly be `[]` (initialized-empty, everything unclassified). No tool, multiple tools, malformed, duplicate or oversized output is a reported initialization failure. An empty response is not accepted as empty initialization. Extraction is not semantically checked: a single paragraph may contain multiple requirements, and literal phrase overlap is not coverage proof. A wrongly accepted extraction remains fixed for this prototype; original text and unclassified entries remain available.

## Record attributes, views and boundaries

The internal catalog is a fixed string list in the existing task-scoped bundle, not a new memory record/index. No R identifiers are created or shown. New knowledge/procedural/GAP saves require `requirements: [supplied sentence, ...]`, allowing multiple choices or `[]`. STATUS stays single and has no requirement property. Existing body, ID, E/M/H source references, generated window and memory policy are reused. The assignment is added to the resolved ref before the existing **single atomic bank + refs commit**; there is no later sidecar mapping write. Raw parsed model arguments remain in receipts; only an execution copy strips the property before the original PMA operation.

NFC Unicode, CRLF/CR to LF and outer-whitespace trimming are the only normalization. Inner spaces, punctuation, paths and case remain distinct. Initialization rejects normalized duplicates. Record assignments deduplicate into fixed catalog order. Unknown sentences explicitly fail and stop later operations in that batch; they never create groups. The prototype bounds the catalog to 32 sentences, 512 Unicode characters each and 2048 total. These are protocol limits, not semantic limits or automatic truncation.

The flat view contains each displayed body once, with its original ID, category, requirements and selected-source event range. Grouped views contain ID references to those same rows. Multiple groups can reference one row; repeated references within one group are deduplicated by ID, never content. Unclassified rows are explicitly listed and remain flat-visible. BM25 selection remains upstream: when thresholds apply, knowledge/procedural each select top 20; GAP follows its existing path. **Model groups cover this displayed subset only**, not all records or complete task coverage. No new model tool expands a hidden group or arbitrary hidden ID. The host's `requirement_view.json` exports all active records and groups; it is a diagnostic export, not automatically supplied to P2 or the model.

Ordering uses the minimum/maximum ordinal of selected/inherited source events in this task's actual accepted event table. It is a range of source acceptance, not execution time or summary creation time. TASK-only/unassociated records have unknown event order and follow anchored rows; ties use ID. Different accepted executions with identical outputs remain separate. A shared requirement does not add event sources: selecting E8 never selects E7 through classification.

Input-memory snapshots already freeze the full ref, now including requirements. Candidate-only history formatting exposes the frozen attribute in H directories and historical receipts. When its twice-escaped directory representation would exceed 2500 characters, the directory/metadata returns requirements_paged, count, SHA256 and a read location; the same frozen full list is supplied as pageable requirements JSON parts in the H read. Joining those parts and JSON-decoding preserves every character. This prevents repeated metadata or atomic directory items from consuming the full page budget; it does not truncate the attribute or increase the 8000-character limit. Deleting/replacing active memory does not change it. Sources/context/H retain the existing visibility, grant, hash/task checks and 8000-character full-JSON paging. A directory may appear after long selected source text; two serial read turns cannot guarantee reaching every ancestor. Reading H cannot change memory contents but issuing a handle writes grant metadata, and that I/O can fail explicitly.

## Persistence, failures and recovery

`requirement_attributes_v1` lives in the existing `source_links.json` atomic bundle. It contains task hash, immutable catalog, and cycle checkpoints. New state requires empty knowledge/procedural/GAP/status, refs and events. Opening a nonempty old bank is rejected. The ordinary bank retains exactly its old four keys; never feed the candidate bundle into the strict P2 bank loader. Task ID and original text are immutable; supplied task changes fail. Later task additions can be retained as visible data and unclassified memory, not silently incorporated into the catalog.

Before startup, the complete maintenance invocation (entries, observation, step) and its digest are durably retained under a caller cycle ID. A duplicate completed cycle with identical input returns its saved result without another model call. Reusing its ID for changed input fails. Another pending cycle blocks new cycles. IDs are 1..90 ASCII letters/digits/underscore/hyphen, matching the existing archive restrictions.

Startup failure preserves pending input and all attempts; retry the identical cycle explicitly. Interrupted startup can also be retried explicitly; it may incur another startup call if a response was not accepted durably. Once accepted, catalog persistence and pending phase change are one atomic commit, so interruption before maintenance reuses the catalog and keeps the first maintenance input. An os.replace-success-then-error reconciles the actual committed bundle, as for memory writes.

Maintenance is marked `running` before entry. Hard interruption there is uncertain: earlier actions might have committed. Reopen fails with `recovery_required` and does not replay. Inspect the private bank, journal and pending input. The host-only `agent.requirement_state.acknowledge_interrupted(cycle_id)` marks that cycle abandoned, retains it and its partial bank, and permits an explicitly supplied **new** cycle ID with the retained input if desired. This is an API recovery path, not an automatic CLI retry or rollback. The standard `--resume` runner records startup stages and this invocation's attempted/completed logical calls. A startup error before any archive/config or model call may resume as a new start only with a recorded safe startup stage and zero counts. Once an archive exists, the original committed-state checks apply. It supports safe startup retry and completed-cycle deduplication; uncertain maintenance recovery requires the host API and deliberate fresh-cycle invocation. A returned terminal tool/engineering failure is cached, not retried. Existing tool failures stop later batch operations, preserving prior successful commits. Writes are atomic per tool, not transactional across an entire batch/cycle. The inherited single-host serial requirement remains; concurrent processes sharing one archive are unsupported.

## Reuse, prompt and evidence

Directly inherited PMA memory operations, bank type and BM25 are pinned at `yifannnwu/proactive-memory-agent@89e5c0d6aadfe531a1aee42fd290d48be89973dd`, Apache-2.0, existing vendor LICENSE retained. SourceLinks, context history and archive are this repository's existing A implementation. Requirement extraction, validation, checkpointing and grouping are new local adaptation; no external graph, embedding, dynamic tree or third-party implementation was copied. MAGE/SAM are not claimed to implement this requirement protocol.

The new maintenance SYSTEM appends one organization paragraph to the full delivered A SYSTEM. Existing useful PMA guidance and GAP/status definition remain intact. A separate small startup SYSTEM applies only to extraction. Only knowledge/procedural/GAP save schemas gain `requirements`; status/delete/read schemas keep their prior arguments. `PROMPT_DIFF.txt` and `PROMPT_PROTOCOL.json` freeze actual text/hashes. Default no-op hooks in LinkedSourceP1Agent and InputMemoryHistory preserve old outputs; frozen actual systems, tools and first-input hashes are checked for the three old candidates.

Offline result: **118 tests passed, 0 errors/failures/skips** (95 prior + 23 new); 66 runtime source hashes. Tests use network-denied fake clients. Standalone empty-task demo: 2 cycles, 3 initial logical fake calls, 0 additional calls when resuming completed cycles. It is a manual visible-response scenario, not a semantic result or equivalent rerun of old six cases. Old six input hashes are unchanged. No real profile was loaded; no real model, Task, P2 or native evaluation ran. Semantic coverage, model compliance, memory quality, latency/token tradeoffs and downstream benefit remain untested.
