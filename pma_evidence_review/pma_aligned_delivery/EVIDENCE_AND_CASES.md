## Synthetic human expectations — not model-scored fixtures

These examples define judgment boundaries for review. They are not injected into
production prompts, and no fake-client output is evidence that a model makes the
suggested decision. Exact choices can vary with what is actually useful now.

| Case | Visible situation and available text | Human expectation |
|---|---|---|
| S1: forgotten scope | A report must cover only one region; current export includes all regions. TASK states the restriction; there is no GAP. | Consider TASK alone if it helps correct scope. A separate GAP is unnecessary. |
| S2: useful old memory | An older API record gives the required argument order. Recent steps lack its original receipt, and the current call reverses the order; no visible contradiction or supersession. | Consider the old record. Do not demand fresh proof within eight steps. |
| S3: repeated known failure | A service rejects an expired token; the agent repeatedly retries the same known invalid token with no relevant condition change. A memory records the failure condition. | Consider the relevant memory. Select existing text, without inventing a new authentication plan. |
| S4: justified same-command retry | A transfer times out once; current evidence supports a transient interruption and the agent reasonably retries. | Silence can be appropriate even when command text is unchanged. One failure is not a permanent prohibition. |
| S5: version/scope promotion | A check covered an older draft or only one requested component; the agent claims the current full deliverable is complete. TASK/current candidates preserve the relevant scope. | Consider the minimum useful original set. Do not demand hypothetical future environments or hidden tests. |
| S6: correctly addressing work | The agent identifies the unmet requirement and has a reasonable current plan that addresses it. | Silence can be appropriate. The plan still does not prove completion. |
| S7: claim versus actions | The agent says it is addressing a restriction but its current actions still contradict it. | Do not treat the statement alone as handling the issue; consider the relevant task/record. |
| S8: overstated memory | A broad success memory conflicts with limited current observations; TASK remains useful. | Do not blindly forward the broad memory. TASK may help; the selector must not rewrite memory into new advice. |
| S9: unknown versus failure | A requested workbook check has not been observed; the agent neither claims completion nor acts against it. | Unknown is not failure. Do not invent a defect or an automatic reminder merely from missing recent proof. |
| S10: repeated checkpoint | The same prior timeout appears again in a checkpoint, without a new actual action. | Keep one historical attempt; re-reading does not establish another attempt. |
| S11: result pending | A distinct actual execution is visible but its result has not returned. | Preserve the attempt with unknown outcome; do not omit it or call it a failure. |
| S12: blocker versus goal | An original gap has two still-unmet conditions; a compiler blocker is resolved while the final publication condition is not. | Revise the same gap and retain the remaining condition; do not retire the whole original goal. |

Protocol negatives remain engineering cases: unknown/repeated aliases, status or
trajectory selection, JSON/free reasoning, mixed tags, malformed fences, wrong
call/cycle/task/revision and stale pending delivery are rejected by existing code.
That parser correctness is separate from whether a valid alias choice is useful.
