# Simple predictive-memory variant

Based on `1272f883aea9e8ffb61fa78f7c610537f2b10f64`, for the full upstream-PMA GA adapter (`GA_PMA_UPSTREAM_ENABLED`), not the separate legacy `GA_PMA_ENABLED` path.

- P1 has one `memory_add(content)` tool. It sees the full saved bank without categories and saves information expected to be useful in the next 10 turns. No forced write and no automatic expiration, deduplication, edit or delete.
- Entries are physically stored in the existing knowledge list for persistence compatibility; the P1/P2 display is a flat bank. Legacy procedural entries are shown too. The old >50-item BM25 prefilter is disabled for this variant, so prompt size can grow without bound.
- Before the first actor call, P1 and P2 run once on the task description and existing bank, without counting that initialization toward the eight-step batches. After eight new eligible actor steps, P1 and P2 run together. Normal and parse-error actor steps count; provider-cancelled and completed events do not. The original task description is included alongside each batch. There is no inference for an incomplete terminal tail; the archive reports its count and attempt IDs. P2 judges whether a memory-based reminder is needed now, rather than requiring evidence of forgetting or a repeated failure. Visible information may still warrant a reminder when current actions do not appear to take it into account. It defaults to silence and keeps the original output parser; its bank contents and cadence change.
- The GA bridge carries actual visible text and tool calls in order, the actor input prepared for the current call after reminders, and the post-step tool-result/framework content prepared before any next-call reminder. It no longer replaces the framework prompt merely because history exists. GA's own visible synthesized summaries are retained; native provider thinking/redacted-thinking blocks are not copied. The actor input is a prepared snapshot, not proof of delivery; transport/request records establish delivery. Tool objects are serialized for PMA. Final visible response is archived without triggering a terminal inference. Unknown response block types or unsupported non-native clients fail explicitly rather than silently omitting actor-visible data. The post-step and subsequent prepared-input views are retained separately; overlapping content can appear twice, and the input cost must be measured. Actor tool dispatch and its actual request builder remain unchanged.
- Original PMA catches phase errors, and an accepted timeout has an unknown outcome; a triggered batch does not guarantee either phase succeeded. The implementation does not automatically replay a batch.
- `tests/test_simple.py` includes ten focused offline checks. This sparse-workspace check uses a `shortuuid` substitute and isolates two classes with AST extraction. It is not a full GA/Harbor integration test. No real model or task evaluation was run.

- `tests/test_pma_actor_input_parity.py` adds four focused native input and response-projection checks; the bridge fixture has six targeted tests. Local tests may use isolated class loading and stubs, so full-runtime acceptance remains separate.
